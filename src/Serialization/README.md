# SDB database loader

This C# code reconstructs the **SDB block envelope and schema metadata**, not the original source or the entire object database. The IDA database maps the raw `FirefallClient.exe` file at address zero: addresses below are **file offsets**, not process virtual addresses.

| Offset | Observed behavior |
| --- | --- |
| `0x130FEE0` | Opens the named source and invokes the block loader. |
| `0x1310060` | Checks magic `DA7ABA5E` and version `12`, scans blocks, selects the first block with matching bit `0x10`, requires build ID `prod-1962`, decrypts bit `0x01`, rejects wrong-endian bit `0x02`, inflates bit `0x04`. |
| `0x12EE010` | Reads the NUL-terminated block name. |
| `0x12F16D0` | FNV-1a name hash with additional integer mixing for the stream seed. |
| `0x12E2F70`, `0x12E3080`, `0x1317410` | MT19937 and payload XOR, one 32-bit output per word and one output per trailing byte. |
| `0x13172C0` | zlib payload preceded by decoded size and a zero word; decoded-size limit `0x10000000`. |
| `0x13106F0` | Parses record marker `1002`, a `u16` table count, table headers, per-table field headers, and sorted row offsets/counts. |
| `0x1311BD0`, `0x1311100` | Maps fields by hash and converts values into runtime structures. The fallback data transform and identical-layout pass-through decision are reconstructed; the differing-layout path's row-buffer allocation, per-row initializer, conversion-status bitset, and final callback flow are documented below. |
| `0x1310600` | Compares two runtime table layouts to choose the identical-layout fast path. The checked descriptor subset is reconstructed in `SdbRuntimeLayout.cs`. |

All multibyte values are little-endian. File header is two `u32`s; each block starts `u32 payloadLength`, `u32 flags`, two presently unidentified `u32`s, a NUL-terminated single-byte build identifier, padding to the next `0x80`-byte file boundary, then payload. The loader compares that identifier to `prod-1962` at PE VA `0x1C15EAC` (raw `0x1814AAC`); the adjacent binary string says `Firefall (v1.5.1962)`. Decoded records start with `u32 1002`, `u16 tableCount`; each table header reads `u32 nameHash`, `u16 rowStride`, `u16 fieldCount`, `u16 nullBitmapOffset`, `u8 unknownC`; each field header reads `u32 nameHash`, `u16 valueOffset`, `u8 nullBit`, `u8 type`. An array of `u32 rowOffset, u32 rowCount` pairs follows, then a `u32` trailing-data offset. The table and field offset names are supported by parser assignments at raw `0x13107xx`–`0x1310Axx` and row mapper accesses at `0x1311C23`, `0x1311E65` and `0x1311E71`; the meaning of `unknownC` and the two envelope words remains unresolved.

Flag `0x08` influences the original parser's runtime allocation path after the descriptors have been read; this offline parser retains the flag but does not emulate that runtime state.

`SdbFieldTypes` exposes the 26 nonzero type IDs, labels and stored byte widths inferred from the descriptor table referenced at **PE VA** `0x1C5A3B8` (actual raw file offset `0x1858FB8`). The names are adjacent literal strings and repeated labels (notably vector and integer types with different widths) may encode handles or alternate representations; they are not definitive C# types. Type ID `0` is an unmapped sentinel. The parser preserves raw type bytes for inspection; native descriptor construction stores type `0` whenever the byte is at least `27` (comparison at raw `0x1310C74`). `SdbRuntimeTableLayout.FromSdbTable` applies this normalization while expanding parsed offsets, hash and null-bit index to the runtime layout model.

The broken type-dispatch decompilation at raw `0x1311100` can be diagnosed precisely: its jump table is at **PE VA** `0x1712490`, raw `0x1311890`. Its 13 absolute VA entries translate to raw code offsets `0x1311204`, `0x1311281`, `0x131130C`, `0x13113A3`, `0x1311413`, `0x131149F`, `0x131151A`, `0x131157F`, `0x13116CE`, `0x1311781`, `0x131116B`, `0x13115DB`, `0x1311847`. The current IDA raw mapping instead treats those VA values as code addresses in unrelated sections. Direct disassembly of the corrected targets establishes the subset implemented by `SdbFieldConversion`: identical known types copy their stored bytes, type IDs 1–8 convert among fixed-width integers by source-signed widening or low-bit truncation, and F32/F64 interchange uses SSE scalar widening (`0x131176C`) or narrowing (`0x131181F`). The float dispatch byte tables at raw `0x1311B68`/`0x1311BAC` and target tables at raw `0x1311B40`/`0x1311B84` confirm these destination cases. F16 to F32/F64 uses the 65536-entry lookup table at **PE VA** `0x1C165B8`, raw `0x18151B8`, through cases `0x131169B`/`0x13116B1`; all 65536 table entries were checked against the bit expansion implemented here. F32/F64 into F16 uses the helper at raw `0x12CB220` (F64 first narrows to F32), reached by wrappers including `0x1315850` and `0x1315990`. Unlike the standard C# `Half` conversion, the native path rounds halfway mantissas upward and maps both signs of zero, and underflow below half-subnormal range, to positive zero.

The integer-source dispatches at raw `0x1311204`–`0x131157F` select F32, F64 and F16 destinations via their translated byte/jump tables. IDs 1–2 and 5–7 sign/zero-extend to 32 bits before SSE `cvtdq2ps`/`cvtdq2pd` (for example `0x1311250`, `0x1311268`, `0x1311554`). Unsigned 32-bit input first becomes an exact double using a signed conversion plus `2^32` compensation (`0x1311357`, `0x131137F`, wrapper `0x1314FA0`), then narrows for F32/F16. The 64-bit inputs pass through signed/unsigned double-conversion helpers at `0x159E20F`/`0x159E17E` before optional F32/F16 narrowing (cases `0x13113DF`–`0x1311412` and `0x13115A7`–`0x13115DA`). C# `double` conversions model these numeric results; hardware rounding mode and exceptional runtime floating-point state are not modeled.

The F16, F32 and F64 source dispatches (`0x13115DB`, `0x13116CE`, `0x1311781`) directly use `cvttss2si`/`cvttsd2si` for byte, 16-bit and signed 32-bit destinations, then store only the destination's low bytes. The reconstructed direct subset covers destination IDs 1, 2, 5, 6 and 7, including SSE's `0x80000000` indefinite result on invalid/out-of-range 32-bit conversions when exceptions are masked. Destination IDs 3, 4 and 8 use 64-bit conversion helpers at `0x159DE70`/`0x159DE7F`/`0x159DE8E` for F32 (after F16 expands), and `0x159E051`/`0x159E060`/`0x159E06F` for F64. Their finite-value outputs truncate toward zero; the first returns only the low 32 bits, while the other two return 64 bits. Their guards use `[-2^63, 2^63)` for signed/low-32 paths and `[-2^63, 2^64)` for the unsigned-64 path, with `0x8000000000000000` as the invalid result (low 32 bits zero). The bound constants are at PE VAs `0x1B3F020`, `0x1B3F028`, `0x1B3F030` (raw `0x173DC20`, `0x173DC28`, `0x173DC30`). The C# reconstruction preserves these values but not the native x87 exception signaling or altered floating-point control state. Compound conversions remain unsupported.

`SdbRuntimeTableLayout.HasIdenticalStorageLayout` models the direct comparison at raw `0x1310600`, called from the row mapper at `0x1311CDB`. It compares table hash (+4), row stride (+8), field count (+20), and each 20-byte field descriptor's name hash (+4), value offset (+12), and type ID (+16), in order. It deliberately **does not compare** the table null-bitmap offset (+12) or a field's null-bit index (+8), even though the row mapper later reads those values. This is an observed fast-path decision, not a general-purpose schema equality test. For nonempty tables the mapper checks `rowOffset + rowCount * rowStride <= decodedLength` and requires a nonzero stride (`0x1311C1E`–`0x1311C61`); the offline parser validates these bounds before exposing descriptors.

When layouts differ, the mapper at `0x1311BD0` scans source descriptor hashes in order for every destination field (`0x1311D26`–`0x1311D58`), recording the first match's zero-based index or `-1` when absent. `MapSourceFieldsByHash` reconstructs that map. The mapper checks per-row source null bits at row base + table null-bitmap offset (+12) + field null-bit index (+8) divided by eight; `0xFF` means the field has no null bit (`0x1311E65`–`0x1311EA6`). `IsSourceFieldNull` reconstructs this check with bounds validation. On a null source, a present destination null-bit index is set in its row (`0x1311EAC`–`0x1311ED2`); `MarkDestinationFieldNull` reconstructs that operation. The mapper calls `0x1311100` for present fields.

For a nonempty table, the mapper first constructs a 0x20-byte result holder (`0x1311C7E`–`0x1311C95`) initialized with the destination layout and source row count. If the layouts compare identical, it skips the map, destination buffer allocation, per-row initializer, and field conversion; the result's row-data pointer stays set to the decoded source's first row (`0x1311CD5`). If layouts differ, it reserves a flat destination buffer of `rowCount * destinationRowStride` bytes using `0x12CBCB0` (`0x1311D75`–`0x1311D7F`), then calls the destination layout's `+0x1C` function once per row with that row's destination address (`0x1311DB0`–`0x1311DC3`). A bitset sized to the destination field count (`Sdb_CreateFieldConversionWarnedBitset`, raw `0x1312B40`), all bits initially `1`, is created **once before the row loop** (not per row) and reused across every row (`0x1311DEC`). **Resolved**: this bitset tracks, per destination field, whether a type-conversion failure warning has *not yet* been logged for that field in this call. The current bit is passed as `Sdb_ConvertFieldValueByType`'s 6th argument and then overwritten with the conversion's success/failure result (`0x1311F40`–`0x1311F9A`). Inside the converter, every unsupported type-ID pairing falls through to a shared handler (raw `0x1311847`) that checks this bit: if it is `0` (already warned for this field), it silently returns failure; if `1`, it resolves both type names (table `dword_1C5A220`, clamped to the literal string `"DBTYPE_INVALID"` for type IDs `>= 0x1A`) and logs `"Could not convert field %s (%s) to %s"` before returning failure. Net effect: an unsupported field/type conversion logs at most **one** warning per destination field per `ConvertRows` call, regardless of how many rows hit it — the bitset is a log-spam suppressor, not a correctness mechanism.

After either layout path, if destination layout `+0x20` is non-null, it receives `(rowCount, firstRowAddress, &destinationRowStride)` and its return value is stored in result-holder `+0x0C` (`0x1311FDF`–`0x1311FF6`); otherwise that field receives `firstRowAddress`. For zero rows, the mapper returns before constructing the result holder (`0x1311C18`). This recovers the branch and callback wiring, not callback implementations or ownership rules. The native same-layout path can therefore expose rows backed by the decoded input; the offline C# converter always returns independent byte arrays and does not emulate either native path.

That `+0x14` offset instead belongs to the *locally parsed* table node found for this file (see below). The paragraphs below replace the previous (incorrect) "entry+0x14" description.

### The static table catalog

The parser's destination-layout catalog is supplied through the database object at `this+4` (a plain field, not a pointer-to-pointer): it is treated as an array-like object with count at `+4` and pointer array at `+8` (`0x1310E20`–`0x1310E34`). At global init (`helper_multicall_130FCB0`, raw `0x130FCB0`) this field is set to a default/sentinel object; no code was found anywhere in the binary that *replaces* it afterward, so the 575 catalog entries present in the shipped binary (count `0x23F`, entry-pointer array at PE VA `0x1DD9EF0`) are **static, compiled-in reflection data** — effectively the row-mapper's schema table is baked into the executable at link time, not built by a runtime "register table" call. This resolves the open question from the previous session: there is no registration routine to find because registration is not a runtime step here.

Each catalog-entry pointer references a struct (example 1 at PE VA `0x1DDCC44`, raw `0x19DB044`, table hash `0x8E3A6BCC`; example 2 at raw `0x19DC124`, table hash `0x4CCBB136`). `+0x00` is **not** a vtable: it points to NUL-terminated ASCII text for the entry's own hash (`"0x8e3a6bcc"` and `"0x4ccbb136"` respectively), matching the DWORD at `+0x04`. The entry fields are `+0x04` table hash, `+0x08` **destination** row stride, `+0x0C` unknown (`6` in example 1, `0x1B` in example 2), `+0x10` reserved/`0`, `+0x14` **destination** field count, `+0x18` destination field-descriptor array pointer, `+0x1C` per-row init callback, `+0x20` finalize/wrap callback (which can be `NULL`), `+0x24` optional teardown callback, and opaque raw DWORDs at `+0x28/+0x2C`.

A read-only scan of all 575 compiled catalog entries refines those last two fields: **573 entries** have a `+0x28` pointer to lowercase text of the form `"0x"` plus eight hex digits, and parsing that text gives the exact `+0x2C` DWORD. Entry index10 (table hash `0x69CE585D`) is an exception: `+0x28` points to `"hands"` and `+0x2C` is a relocated pointer to `"backpack"`. Entry index19 (table hash `0xFDA606A8`) stores `0xFFFFFFFF` in both slots. The PE relocation table has `HIGHLOW` entries for 574 of 575 `+0x28` slots and for only the pointer-valued `+0x2C` slot in entry10. Thus `+0x28` is usually a pointer, while `+0x2C` can be either a scalar-looking DWORD or a pointer; their repeated hex pairing is not a universal invariant. No traced parser, mapper, comparator, or reset path consumes either field, so keep both opaque and do not infer a checksum or semantic name.

For example 1, the optional `+0x24` callback is raw `0x712920` (`Sdb_RowHandleArrayDestroyCallback_Example`); example 2 leaves it `NULL` alongside a `NULL` `+0x20`. The callback's reset-time use is described below. The destination field-descriptor array uses the same 20-byte shape as decoded source descriptors: `+0x00` points to that field's hash-as-hex string (verified for field 0 of example 2: `"0xcffdfb53"`), `+0x04` hash, `+0x08` null-bit index or `0xFF`, `+0x0C` value offset, and `+0x10` type.

During parsing (`Sdb_ParseDecodedBlock`, raw `0x1310C00`), the code walks **every** catalog entry (`0x1310E20`–`0x1310E8E`) and, for each one, searches a *separate*, per-parse red-black tree built from the file's own decoded tables (`Sd2_CreateFieldMapNode`/`Sd2_FieldMapInsertOrFind`, keyed by the file's table hashes) for a node whose key equals the catalog entry's hash. On a match, it calls `Sdb_ConvertRowsByFieldMapping(databaseObject, blockBase, blockLength, catalogEntry, matchedLocalNode + 0x14)` (`0x1310E91`–`0x1310E9E`): the **catalog entry pointer itself** is the function's `a4` destination-schema parameter, and `matchedLocalNode + 0x14` (a small 3-word struct: pointer to the file's own decoded 40-byte table descriptor, an extra word, and the row count) is `a5`, the source-schema parameter. So the catalog supplies what the compiled client *expects* a table named by that hash to look like (including C++-object construction callbacks); the decoded file supplies what is *actually on disk* for that same hash; `Sdb_ConvertRowsByFieldMapping` reconciles the two.

One worked callback example (table hash `0x8E3A6BCC`, destination stride 8 bytes, 3 fields at byte offsets 0/4/5 with types 3/1/1): the `+0x1C` init callback (`Sdb_RowInitCallback_ClearField_Example`, raw `0x712800`) zeroes a 16-bit field at `rowPointer+4` — exactly spanning the two 1-byte fields at offsets 4 and 5 — before real values are written; the `+0x20` finalize callback (`Sdb_RowFinalizeCallback_BuildHandleArray_Example`, raw `0x712820`) allocates `rowCount * 8` bytes and fills them with lightweight 8-byte **row-handle** records (`{vtable = &unk_1C6883C, dataPointer = convertedRowsBase + index * rowStride}`), writes `8` into the destination-stride out-parameter, and returns that handle array. That handle array — not the raw converted row buffer built earlier — becomes the mapper result's exposed rows pointer (result `+0x0C`). This shows that, for at least this table, the public "converted rows" the client ultimately iterates are thin polymorphic view objects pointing back into the real row data, rather than the row struct array itself. Both callbacks are schema-specific compiled thunks (the constants `4`, `8` are baked in per table), so other tables almost certainly have their own distinct init/finalize callback pairs with the same *shape* but different constants. A second, different example (table hash `0x4CCBB136`, raw entry at `0x19DC124`, stride 28, 9 fields) confirms the pattern generalizes but is not identical: its `+0x1C` init callback (`Sdb_RowInitCallback_SetDefaults_Example2`, raw `0x741A30`) does not merely zero bytes — it writes float `1.0f` (`0x3F800000`) into row offsets 0 and 20, zeroes offsets 8 and 12, and zeroes single bytes at 24 and 26, i.e. it establishes real per-field default values (C++-constructor style), not a blanket memset. Its `+0x20` finalize callback is **NULL**, confirming the mapper's documented fallback (result `+0x0C` receives the raw converted-row buffer address directly, with no wrapping handle array) is a real, exercised code path and not merely theoretical. **This callback's writes were cross-checked byte-for-byte against the table's 9-field descriptor array (offsets/types: `0`/`9`, `4`/`3`, `8`/`9`, `12`/`11`, `16`/`3`, `20`/`9`, `24`/`1`, `25`/`1`, `26`/`1`)**: every write's offset and width lines up exactly with `SdbFieldTypes`' documented storage size for each type (type `9`=F32/4B, `3`=U32/4B, `11`=`char`/4B, `1`=U08/1B) — the two F32 fields (offsets 0, 20) default to `1.0f`, the other F32 field (offset 8) and the `char`-typed field (offset 12) default to zero, and two of the three U08 fields (offsets 24, 26) default to zero while the third (offset 25, and both U32 fields at offsets 4/16) are left untouched (implicitly zero from the destination buffer's allocation). This independently confirms the storage-byte-width table against real callback behavior, not just the static type-descriptor table it was originally inferred from. `Sdb_OpenAndLoadDatabase` (`0x130FEE0`) supplies the database object and path that `Sdb_ParseDecodedBlock` uses to reach this catalog. The first example's catalog entry `+0x24` callback, `Sdb_RowHandleArrayDestroyCallback_Example` (raw `0x712920`), is the teardown counterpart to `+0x20`'s builder: given a non-null array pointer and nonzero count, it walks the array at an 8-byte stride (matching the handle record's `{vtable, dataPointer}` shape built by `+0x20`), invokes each element's vtable slot `0` with argument `0` (a per-handle release/dispose call), then frees the array buffer through the generic allocator helper; a non-null count with a null array pointer instead logs an internal consistency error. It takes no table-specific baked constants (unlike the init/finalize callbacks), so it may be a shared destroy routine reused wherever a handle array of this exact shape is built, though it still shows zero static code xrefs (like `+0x1C`/`+0x20`, it is only reachable indirectly through the catalog entry's function pointer, never called directly from traced code) — no consuming call site has been located.

The row-handle vtable pointer in that example is PE VA `0x1C6883C`, at raw file offset `0x186743C` according to the PE section table; its first two entries are `0x00B0DFF0` and `0x00B25720`, mapping to raw code offsets `0x70D3F0` and `0x716B20`. Slot 0's bytes begin `55 8B EC F6 45 08 01 56 8B F1 C7 06 30 88 C6 01`; it writes the object vtable to `unk_1C68830`, tests the low bit of the first stack DWORD, and conditionally calls raw offset `0x12C8D60`. Slot 1 begins `8B 0D 54 FC E4 01 A1 50 FC E4 01 C7 05 48 FC E4 01 00 00 00 00`; direct instruction decoding shows it clears several globals and zeroes a 16-bit member at `+8` in 12-byte entries across a global range. The purpose of those actions relative to this row-handle type is not established; neither slot is named as a generic destructor beyond the direct call behavior. `Sdb_InitConvertedTableResult` at raw `0x130FBD0` initializes holder `+0x18` to null, and the traced row mapper does not assign that field. Reset releases it only when non-null, so its non-null producer, if any, remains unknown. `SdbNativeRowHandle32` and `SdbNativeRowHandleVTable32` preserve the observed pair layout and address constants without implementing either native call.

The parser reports malformed inputs rather than guessing a schema; it returns decoded bytes and descriptors for later row analysis. `SdbBlock.GetRawRow(tableIndex, rowIndex)` copies the corresponding `rowStride` bytes from `rowOffset + rowIndex * rowStride`, mirroring row address calculations at `0x1311CD5` and `0x1311E1B`. `GetRawField` checks the field's null bit and returns `null` if set, otherwise copies its recorded storage width from `row + valueOffset`. The latter can represent an opaque handle or compound value; it is **not** a decoded object. Invalid field bounds or unknown widths fail explicitly. Memory consumption follows the original loader's generous decompression limit, so do not use this implementation on untrusted files without an application-level size cap. The database's original exception/logging and allocator behavior are not reproduced.

`SdbRowConverter.ConvertRows` applies the reconstructed fallback field-hash map to every source row, calls `SdbFieldConversion` for supported scalar type pairs, sets destination null bits for mapped null fields, and leaves unmapped destination bytes zero-initialized. It requires matching table hashes and returns independent row byte arrays. This is a standalone value-layout conversion, not the client's native result-holder, allocation/callback, or identical-layout fast path; it deliberately does not emulate per-row initialization, the conversion-status bitset, or unknown fields.

`Sdb_ResetLoadedDatabaseState` (`0x1312030`) is called before reloading a populated database and during client shutdown. It invokes the owning object's vtable slot `+8` when byte `this+9` is set, then clears that flag. It walks the tree rooted at `this+0x34`; each non-null payload may invoke its vtable slot `+0x24` with payload members `+0x0C` and `+0x04`, releases the refcounted object at payload `+0x18`, and is then freed. The tree nodes are subsequently destroyed and the tree header reset; `this[14]` is cleared, `this[8]` and `this[9]` are zeroed, and a method at the object referenced by `this[15]` plus `0x14` is called. A flag at `this+0x1C` gates a walk over the separate tree at `this+0x28`, where node payloads at `+0x14` are released; that tree is destroyed and `this[11]` cleared. Finally the refcounted object at `this[12]` is released/freed when present, and `this[4..6]` are zeroed. These offsets describe observed cleanup operations, not reconstructed database field names.

**Two distinct database trees.** Comparing this function's cleanup against each tree's own range-erase helper shows they have different layouts and ownership paths:
- The tree rooted at `this+0x34` (embedded header, in-place) is the **payload tree**: each node's value at node `+0x14` is a pointer to a small struct with its own vtable (`+0x00`), an optional release callback at vtable slot `+0x24` (taking the payload's `+0x0C`/`+0x04` members), and a dual-refcounted handle at `+0x18` (classic strong/weak `InterlockedExchangeAdd`-based release: the first counter reaching `-1` invokes the handle's vtable slot `0`, the second then invokes slot `1`). After release, the payload's `+0x10` is stamped with a sentinel vtable (`unk_1C5FC14`) before the node is freed. This is real, non-trivial per-entry resource ownership.
- The tree at database `this+0x28` is a **separate auxiliary buffer map**, not the result-holder tree. The database field `+0x28` holds a pointer to a separately allocated `0x18`-byte header, and database `+0x2C` is its entry count. Header links are `+0x00` leftmost, `+0x04` root, and `+0x08` rightmost. Its `0x18`-byte nodes hold left/parent/right links at `+0/+4/+8`, balancing/sentinel bytes at `+0x0C/+0x0D`, an opaque DWORD key at `+0x10`, and a pointer-like value at `+0x14`; `SdbNativeDatabaseTree28.cs` preserves these as 32-bit address tokens and leaves the key uninterpreted.

  `0x13122D0` derives a key from the low bit of its input: one branch uses `(value >> 1) + 2`, the other `(value >> 1) & 0x7FFFFF`. That same derived DWORD is used as a displacement from the database backing-buffer pointer at `+0x20`, and `key + length` is checked against the length at `+0x24`. If the context at `+0x30` is non-null, the routine looks up the key through `0x13125F0`; a hit returns node `+0x14`, while a miss inserts `[key, valuePointer]` via `0x1316120`/`0x1316150`. This is not established as a table hash or named domain identifier.

  Reset releases node `+0x14` values only when database byte `+0x1C` enables that pass, then destroys the nodes, self-links the header and clears the count while retaining database `+0x28`. The destructor path at `0x130FE30` clears nodes and frees the header. It does not visibly release every node value; whether reset always precedes destruction or another path handles those values remains unresolved, so no universal ownership claim is made.
